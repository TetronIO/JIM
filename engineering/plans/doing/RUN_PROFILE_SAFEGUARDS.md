# Run Profile Safeguards: Implementation Plan

- **Status:** Doing
- **Issue:** [#1618](https://github.com/TetronIO/JIM/issues/1618)
- **PRD:** [PRD_RUN_PROFILE_SAFEGUARDS.md](../../prd/doing/PRD_RUN_PROFILE_SAFEGUARDS.md)

## Overview

Two stacked layers, in the #1605 pattern. Layer 1 delivers the three export limits end to end: model, migration, a per-run decision ledger, the export server's two passes, the worker's warning and counters, REST, PowerShell, portal, docs. Layer 2 delivers the two Full Import deletion limits end to end, the hook into the #1605 gate, and the share-comparison helper shared with the post-clear shortfall check. The PRD's five decisions apply: in particular, a run that would exceed a limit attempts none of that change type (Decision 4), and there is no run-time override (Decision 5). Design rationale and the target look: the Run Profile Safeguards artefact linked from the issue.

Implementation is orchestrated: a sub-agent implements each layer from this plan, red-first; the orchestrator reviews every diff against the PRD before it is committed, and runs the runtime verification.

## Phase 1: Export limits (branch `feature/run-profile-safeguards`)

1. **Model and migration.** `ConnectedSystemRunProfile` gains `int? MaxCreates`, `int? MaxUpdates`, `int? MaxDeletes` (XML docs: Export run type only; null is no limit; zero attempts none). `Activity` gains `int? ExportCreatesWithheld`, `int? ExportUpdatesWithheld`, `int? ExportDeletesWithheld` (populated on every Export run, null elsewhere). One migration, `AddRunProfileExportLimits`, six nullable integer columns, no backfill. The existing `RequiresPostgres` head-migration fixture covers it.
2. **Ledger.** New `ExportChangeLimitLedger` in `JIM.Application/Services`: a per-run decision built from the three limits and the executable Pending Export count per change type, taken once at the start of the run through a new `ISyncRepository.GetExecutableExportCountsByChangeTypeAsync` (one GROUP BY on the same executable predicate as the existing count; Postgres and in-memory implementations). A type whose count exceeds its limit is withheld in full; a type within its limit, or without one, runs in full; a limit of zero withholds whenever anything is pending. `Reserve(type, requested)` grants everything for an allowed type and nothing for a withheld one, so every hook point below keeps one shape; `IsWithheld(type)`, `Withheld(type)` (the pending count at start for a withheld type), `Limit(type)`, `AnyWithheld`. Tests: no limit; count below, equal to and one over the limit; zero limit with and without pending exports; the count query on both providers.
3. **Options and result.** `ExportExecutionOptions` gains the three nullable limits; `ExportExecutionServer` builds one ledger per run so both passes share it. `ExportExecutionResult` gains `CreatesWithheld`, `UpdatesWithheld`, `DeletesWithheld`.
4. **Server, first pass.** `ExecuteExportsAsync` builds the ledger once, after the executable count, and shares it with both passes. The paging loop of `ExecuteUsingCallsWithBatchingAsync` passes the withheld change types to `GetExecutableExportBatchAsync` (a new optional exclusion parameter, Postgres and in-memory), so withheld rows are never read; the withheld totals are added to the processed count at the start so the progress window completes. The in-memory filter (`ReserveAgainstLedger`) stays on every path, batch loop, files path and deferred pass alike, as the guard: under this ledger it drops a withheld type wholesale and passes an allowed type untouched. Nothing withheld is marked, failed or given a `ProcessedExportItem`; it stays Pending.
5. **Server, deferred pass.** In `ProcessDeferredExportsAsync`, the same guard runs before `exportsToWrite` is split into batches. A withheld type's deferred exports are left exactly as the first pass left them (Pending, unresolved-reference flags untouched) and are not marked deferred; an allowed type completes there in full.
6. **Worker.** `SyncExportTaskProcessor` passes the Run Profile's three limits into the options. `ProcessExportResultAsync` copies the withheld counts onto the Activity, sets `ObjectsProcessed` to attempted plus withheld, and for every withheld type appends one sentence to `WarningMessage` (newline-separated, as the unresolved-reference summary is) built by `ExportOutcomeMessage.ForWithheld(type, limit, pending)`: "Max deletes is 100, but 342 deletes were pending, so none were attempted and all 342 remain pending. Check what staged them, then raise or clear the limit on this Run Profile, or run an Export Run Profile without the limit." Singular forms for one. `CompleteActivityBasedOnExecutionResultsAsync` already turns a warning message into Complete with warning.
7. **Validation.** `RunProfileSafeguardsValidator.Validate(ConnectedSystemRunProfile)` in `JIM.Application/Services` returns null or a message naming the first offending field ("MaxDeletes can only be set on an Export Run Profile."; "MaxDeletes cannot be negative."). Called from both overloads of `CreateConnectedSystemRunProfileAsync` and `UpdateConnectedSystemRunProfileAsync` (throwing `ArgumentException`) and from the controller (400). Unit tests per rule.
8. **REST.** `RunProfileSafeguardsDto` with the three members (Layer 2 adds two). `RunProfileDto.Safeguards` always present. `CreateRunProfileRequest.Safeguards` optional. `UpdateRunProfileRequest.Safeguards` optional; when present it replaces all members, a null member clearing that limit. `ActivityDetailDto` gains the three counters. Tests in `test/JIM.Web.Api.Tests/`: mapping both ways, replace-all semantics, 400 on the wrong run type. Regenerate the OpenAPI document with the repository's generation script and confirm the new members appear.
9. **PowerShell.** `New-JIMRunProfile` and `Set-JIMRunProfile` gain `[Nullable[int]]` parameters `-MaxCreates`, `-MaxUpdates`, `-MaxDeletes`. New sends `safeguards` when any is bound. Set fetches the current Run Profile, merges the bound parameters (an explicit `$null` clears; verified: `$PSBoundParameters` records a parameter passed `$null`), and sends the whole `safeguards` object only when at least one is bound. Comment-based help, parameter aliases per `src/JIM.PowerShell/CLAUDE.md`, Pester tests in `RunProfiles.Tests.ps1`.
10. **Portal.** `ConnectedSystemRunProfilesTab.razor`: a Safeguards group in both dialogs for the Export run type, three `MudNumericField<int?>` in a row with the helper text from the mock; a chip per configured limit beside the run type in the grid, in the Verification Mode chip's style. `ActivityDetail.razor`: a Safeguards panel, in the Clear Summary panel's style, rendered when any of the three counters is above zero, with the caption from the mock. `ConnectedSystemDetail.razor`: a warning notice under the header buttons when the most recent completed Export Activity for the system withheld anything, naming the Run Profile and the limit reached, linking to the Activity and the Run Profiles tab; one new `ActivityServer` accessor backed by a repository query for that Activity. Build, and run `test/JIM.Web.Tests/` if any component test is touched.
11. **Docs and changelog.** `docs/configuration/run-profiles.md` Safeguards section (the three export limits now; Layer 2 adds the import limits to the same section), with recommended values and a "Letting a legitimate mass change through" paragraph: a second Export Run Profile with no limit, run by hand and kept out of Schedules, because raising a limit and forgetting to restore it removes the safeguard; `docs/configuration/activities.md`; `docs/powershell/run-profiles.md`; `docs/powershell/activities.md`; `docs/concepts/synchronisation-pipeline.md` one paragraph under Export. One ✨ changelog entry under `[Unreleased]` covering the feature; Layer 2 amends it rather than adding a second.
12. **Tests, red first.** Ledger unit tests (step 2); `ExportExecutionTests`-style tests through the in-memory harness: one over the limit withholds the whole type with every export still `Pending` and no execution item, equal to the limit attempts all, zero withholds all, a withheld type stays withheld in the deferred pass while an allowed type completes there, the files path honours the decision, the batch exclusion never reads a withheld row; `ExportExecutionParallelBatchTests` gains one withheld case; message tests; validator tests; API tests; Pester; Scenario 21 Test 1 (below).

## Phase 2: Full Import deletion limits (branch `feature/run-profile-safeguards-stack-import-limit`)

1. **Model and migration.** `ConnectedSystemRunProfile` gains `int? MaxDetectedDeletions` and `int? MaxDetectedDeletionsPercent`; `Activity` gains `int? DetectedDeletionsWithheld` (zero on a Full Import that applied its detection, the withheld count on one that refused, null elsewhere). Migration `AddRunProfileDeletionDetectionLimits`.
2. **Shared helper.** `ShareThreshold.Exceeds(long count, long baseCount, int maxPercent)` in `JIM.Models` (long cross-multiplication; a base of zero never exceeds). `ConnectedSystemServer.StrandedValueSweep.IsReconciliationRefused` delegates to it; its tests stay green.
3. **Two-phase deletion detection.** `ProcessConnectedSystemObjectDeletionsAsync` in `SyncImportTaskProcessor` becomes resolve-then-apply. Phase A (`ResolveDeletionCandidatesAsync`) runs the existing per-type set difference and the per-candidate lookup, with no side effects, and sorts candidates into three lists: not found, already Obsolete, would newly be marked. Phase B checks the count of the third list against `MaxDetectedDeletions` and, through the helper, against `MaxDetectedDeletionsPercent` of the `existingCsoCount` already taken at the call site (passed in). Refused: set `DetectedDeletionsWithheld`, append the warning, log the counts, change nothing, including the stale Pending Export cleanup. Not refused: apply exactly today's behaviour per candidate (the cleanup for the already-Obsolete list, cleanup plus execution item plus status for the new list), and set the counter to zero.
4. **Warning.** `ImportOutcomeMessage.ForRefusedDeletionDetection(count, baseCount, maxCount, maxPercent)` names whichever limit tripped, or both: "Deletion detection found 4,120 objects (41% of 10,000) no longer in the Connected System, above this Run Profile's limit of 10%; none were marked as deleted. Check the Connected System's scope and the connector's filters, or raise the limit, then run the Full Import again."
5. **Gate.** `FullImportSuccessEvaluator.IsSuccessfulFullImport(status, objectLevelErrorCount, detectedDeletionsWithheld)` returns false when the withheld count is above zero; `Worker.cs` passes `Activity.DetectedDeletionsWithheld ?? 0`. Tests per branch.
6. **Validation.** The validator gains: the two fields only on Full Import; percent between 0 and 100; counts not negative.
7. **Surfaces.** The two DTO members and controller handling; the two PowerShell parameters on both cmdlets; the dialogs' Safeguards group for Full Import (two fields in a row, the helper text from the mock); chips; the Activity Safeguards panel's import tiles (withheld, share of Connector Space, limit) and its gate caption; docs (the Safeguards section, the Full Import paragraph in the pipeline concept, the PowerShell references); the changelog entry amended.
8. **Tests, red first.** Through the reflection harness used by `DeselectedObjectTypeDeletionDetectionTests`: at, one above and one below the boundary for the count and for the share; nothing marked and no Pending Export cleanup when refused; already-Obsolete objects excluded from the count; the counter set both ways; the Activity warning text; evaluator tests; validator tests; API and Pester additions; Scenario 21 Test 2.

## Scenario 21: Run Profile Safeguards (integration)

New scenario script reusing `Setup-Scenario1` as Scenario 7 does, registered in `Run-IntegrationTests.ps1` the same way.

- **Test 1 (Layer 1):** CSV Full Import and Full Synchronisation stage a create to LDAP per user; `Set-JIMRunProfile` puts Max creates 1 on the LDAP Export Run Profile; the export runs. Assert: Activity `CompleteWithWarning`, nothing succeeded, `exportCreatesWithheld` equals the pending count, the warning names the limit and the pending count. Set the limit equal to the pending count, export again, assert everything created and the counter zero (at the limit runs in full). Clear the limit with `-MaxCreates $null` and assert it reads back cleared.
- **Test 2 (Layer 2):** put Max detected deletions percent 10 on the CSV Full Import Run Profile; remove a third of the CSV rows; run the Full Import. Assert: `CompleteWithWarning`, `detectedDeletionsWithheld` equals the removed count, the obsolete count is zero, `lastSuccessfulFullImportCompletedAt` unchanged. Raise the limit to 50, run again, assert the objects are now obsolete and the timestamp moved.

## Success Criteria

Per the PRD's acceptance criteria. An Export run with no limits performs no additional database work and one lock acquisition per batch; a Full Import with no limits performs the same lookups as today.

## Risks & Mitigations

- **The count query and the paging predicate drifting apart**, so a type counted within its limit is not what the loop reads: both use the one executable predicate, and a test asserts the per-type counts sum to the existing executable count.
- **A withheld backlog on a frequent Schedule**: each run costs one grouped count and no scan, because withheld types are excluded from the paging query; the Connected System notice is the persistent signal that action is needed.
- **The files export path bypassing the ledger**: applied to both paths; a unit test covers the files path since Scenario 21 exercises the calls path.
- **Two-phase detection changing today's behaviour** (execution item order, cleanup of already-Obsolete objects): phase B replays today's per-candidate sequence verbatim; the existing deletion-detection fixtures stay green.
- **Refused detection counted as a successful Full Import** by the #1605 gate: the evaluator takes the withheld count; a test per branch.
- **Clearing a limit impossible from a script**: the nested `safeguards` object with replace-all semantics and the nullable PowerShell parameters; a Pester test for the `$null` case.
- **OpenAPI document drift**: regenerated in Layer 1 and again in Layer 2.
