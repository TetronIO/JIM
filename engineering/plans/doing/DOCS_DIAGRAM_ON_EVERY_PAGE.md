# A Diagram on Every Docs Page: Implementation Plan

- **Status:** Doing (Phases 1 to 3 done; Phase 4, the Configuration batch, next)
- **Issue:** [#2564](https://github.com/TetronIO/JIM/issues/2564)
- **PRD:** [`PRD_DOCS_DIAGRAM_ON_EVERY_PAGE.md`](../../prd/doing/PRD_DOCS_DIAGRAM_ON_EVERY_PAGE.md)

## Overview

Every customer page on the docs site gets at least one diagram specific to it. A diagram is a short spec written in the page, at the place it appears, as a fenced `jim-diagram` block. A MkDocs build hook renders each spec to inline SVG in the house diagram style, from one of six archetypes:

- flow
- lifecycle
- anatomy
- decision
- comparison
- relationship map

A new `VIS` rule family in the documentation standard makes the rule enforceable. VIS-1 (a page has a diagram) is a Ratchet seeded over existing pages; VIS-2 to VIS-4 are rubric review rules. The Configuration section (41 pages, 2 with a diagram today) is the first batch.

## Business Value

Only 12 of 155 pages have a diagram, yet the concept diagrams are among the site's most effective content. Readers build the picture of a flow, a lifecycle or a structure from prose and tables, which is slower and is forgotten sooner. A per-page spec rendered from shared archetypes makes a diagram a few lines of text rather than a hand-drawn SVG. That turns about 140 diagrams from a design project into routine authoring, and keeps every diagram consistent, themed, accessible and readable on a phone.

## Technical Architecture

### Current state

- Concept diagrams are hand-authored SVGs in `docs/assets/diagrams/`, inlined with pymdownx.snippets.
  - Colours come from `--jimdg-*` tokens in `custom.css`, and the visual language is in `engineering/DESIGN.md` > Diagrams.
  - Edge-label cuts are generated by `scripts/Update-DiagramLabelCuts.ps1`, which measures rendered text in Chromium.
- Mermaid diagrams are fenced blocks that Material renders, with `accTitle`/`accDescr` enforced by A11Y-1.
- `diagram-zoom.js` makes every `svg.jim-diagram` and Mermaid diagram click-to-enlarge.
- One build hook exists: `docs/hooks/changelog.py`, registered under `hooks:` in `mkdocs.yml`.
- `scripts/Test-DocsConformance.ps1` implements the mechanical rules, with tiers in `docs/.conformance/config.psd1` and Ratchet debt in `docs/.conformance/baseline.tsv`.

### Proposed solution

**1. The spec, in the page.** A fenced block where the diagram belongs:

````markdown
```jim-diagram
archetype: flow
title: What a Synchronisation Rule does to an object on its way in
desc: >
  An inbound Synchronisation Rule takes a Connected System Object ... (the full text alternative)
in: { label: Connected System Object, note: Connector Space }
out: { label: Metaverse Object, note: the Metaverse }
container: { label: Synchronisation Rule, tag: "1 Direction: inbound" }
steps:
  - { id: scope, label: Scoping criteria, badge: 2, note: "out of scope: skipped" }
  - { id: match, label: Object Matching Rules, badge: 3 }
  - { id: map, label: Attribute mappings, badge: 5 }
branches:
  - { from: match, to: map, label: match }
  - { from: match, via: { id: project, label: Projection, sub: creates one, badge: 4 }, to: map, label: no match }
```
````

- **Why in the page:** the diagram sits next to the text it depicts, an author changes both in one edit, and the conformance check can count it.
- **Parsing:** the YAML is parsed with PyYAML, which MkDocs already depends on, so there is no new dependency.
- **Shape:** each archetype has its own small schema, validated at build time; an invalid spec fails the build with the page and line.

**2. The renderer: `docs/hooks/diagrams.py`.**

- An `on_page_markdown` hook replaces each `jim-diagram` fence with raw SVG (no blank lines, the same constraint the snippet includes have).
- Per archetype, a layout function computes geometry from the spec and emits SVG using the existing `jimdg-*` classes plus a few new ones.
- **Text measurement:** the renderer needs label widths to size boxes and wrap text. Python has no font metrics without a new dependency, so a committed table `docs/hooks/diagram_metrics.json` holds IBM Plex Sans and Plex Mono advance widths for the weights used. It is generated by a new `scripts/Update-DiagramFontMetrics.ps1`, which measures in Chromium (the same approach as `Update-DiagramLabelCuts.ps1`). A label that will not fit its box at the minimum size fails the build rather than overflowing.
- **Two layouts per diagram:** a wide layout (800 units, drawn at close to body-caption size in the reading column, capped at its design size at full width) and a narrow layout for phones. Both are emitted, and CSS shows one per breakpoint (`display: none` on the other, which also removes it from the accessibility tree). The lightbox already handles any `svg.jim-diagram`.
- **Text alternatives:** `<title>` and `<desc>` come from the spec's `title` and `desc`, both required. A11Y-2 is then satisfied by construction.
- **Edge labels:** edge labels get their cut rectangles from the same metrics. `Update-DiagramLabelCuts.ps1 -Check` is extended to check rendered diagrams on the built site, not only the files in `docs/assets/diagrams/`.

**3. The archetypes.** Each one has a wide and a narrow layout:

| Archetype | Shape | Narrow layout |
|-----------|-------|---------------|
| Flow | Input, steps in a container, branches, output | Steps stacked vertically, branches indented |
| Lifecycle | States, with transitions labelled (cmdlets set in mono) | States stacked, transitions between them |
| Anatomy | A subject (a value, an object) with callouts and property chips | Subject on top, callouts listed beneath |
| Decision | A question tree ending in outcomes | Tree stacked |
| Comparison | Two to four options in columns against shared criteria | One option per block |
| Relationship map | Nodes and labelled links, each node linking to where it is described | Nodes stacked with link labels |

**4. The rules.**

- **VIS-1:** implemented in `Test-DocsConformance.ps1` as a page-level check. It counts `jim-diagram` fences, snippet includes of `assets/diagrams/*.svg`, inline `<svg class="jim-diagram"` and Mermaid fences.
  - Tier `Ratchet` in `config.psd1`, seeded once with `-SeedBaseline -Rule VIS-1`; each batch lowers the baseline with `-UpdateBaseline`.
  - `docs/reference/changelog.md` gets `<!-- conformance: allow-page VIS-1 "released changelog entries, generated from CHANGELOG.md" -->`.
- **VIS-2 to VIS-4:** added to the rubric the documentation review workflow uses, and to the standard's rule index.

**5. Batch review.** A new `scripts/New-DiagramContactSheet.ps1 -Section configuration` builds the site, screenshots every diagram in the section in light, dark and phone views, and writes one HTML contact sheet. This is the artefact each batch is approved from.

### Data flow

```
docs/configuration/api-keys.md          docs/hooks/diagrams.py               built page
  ```jim-diagram            --parse-->    validate spec       --render-->    <svg class="jim-diagram jim-dg-wide">
  archetype: anatomy                      measure with                       <svg class="jim-diagram jim-dg-narrow">
  ...                                     diagram_metrics.json               (CSS shows one per breakpoint)
  ```
```

## Implementation Phases

Each phase is its own pull request. Phases 1 to 3 land before any page gets a diagram, so the Configuration batch is pure authoring.

### Phase 1: Renderer foundation and the first archetype ✅

- `docs/hooks/diagrams.py` with the fence parser, spec validation, the metrics loader, text wrapping and the **flow** archetype (wide and narrow).
- `scripts/Update-DiagramFontMetrics.ps1` and the committed `docs/hooks/diagram_metrics.json`.
- Register the hook in `mkdocs.yml`; add the archetype CSS to the "Concept diagrams" section of `custom.css`.
- **Tests, written first (TDD):**
  - Python `unittest` (standard library, no new dependency) under `docs/hooks/tests/`, covering spec validation errors, text wrapping, box sizing, the narrow-layout switch and the `<title>`/`<desc>` output.
  - The browser check `scripts/Test-Diagrams.ps1` (Playwright, like `Test-DocsLayout.ps1`) renders fixture specs and asserts, in both themes:
    - no text overflows its box;
    - no horizontal page scroll at 390px, 688px and full width;
    - text is at least 10px on screen at 688px and on the phone layout;
    - the label-cut check passes.
- Wire both into `changelog-lint` when `docs/hooks/**`, `custom.css` or the scripts change.

### Phase 2: The remaining archetypes ✅

- Lifecycle, anatomy, decision, comparison and relationship map, each with wide and narrow layouts, each with unit and browser tests.

## Success Criteria

- Every customer page but the changelog has at least one diagram; the VIS-1 baseline is empty and VIS-1 is Block.
- No diagram overflows, causes horizontal scroll, or renders text below 10px at the reading width or on a phone, in either theme (`Test-Diagrams.ps1`).
- Every diagram has a `<title>` and a `<desc>` carrying the same information as the picture.
- Changing a diagram label is a one-line edit in the page.

## Benefits

- **Readers** see the shape of each subject before the detail, and every page has a visual anchor.
- **Authors** add a diagram in a few lines without drawing, and the archetype guarantees the house style, theming, accessibility and the phone layout.
- **Maintenance:** a label lives next to the text it describes, so the two change together, and a renamed product noun is a text edit.

## Dependencies

- No new packages. PyYAML ships with MkDocs; Chromium and Playwright are already used by the diagram and layout checks.

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| Archetypes too rigid, so diagrams look alike | Six archetypes with optional elements (badges, notes, branches, chips); hand-authored SVG stays allowed for the rare diagram no archetype fits; VIS-3 review rejects generic diagrams |
| Committed font metrics drift from the rendered font | Metrics are generated from the same webfont the site loads; `Test-Diagrams.ps1` measures real rendering and fails on overflow |
| A diagram states something the product does not do | VIS-4 in the review rubric; each spec is written against the page and checked against the product; contact sheet review per batch |
| Renderer becomes a large bespoke layout engine | Fixed layouts per archetype, not general graph layout; specs that do not fit fail loudly rather than being laid out cleverly |
| Two SVGs per diagram double the markup | Diagrams are small (a few KB); the hidden layout is `display: none` |
| The planned move from Material for MkDocs to Zensical (#2058) may not run MkDocs hooks | The renderer is a plain function (`replace_fences`) with a command line; it can run as a Zensical extension or a pre-build step if hooks are not supported. The changelog hook carries the same exposure, so the migration has to answer it once for both |
| Build hook ordering with pymdownx | The hook runs at `on_page_markdown`, before Markdown conversion, emitting raw HTML with no blank lines, as snippet includes already do |
